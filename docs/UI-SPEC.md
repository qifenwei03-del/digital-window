# Digital Window — UI 規格

寶舖知行案 C 區數位窗景。1:1 展示螢幕(實體 150 × 150 cm),影片背景 + 可切換的天氣面板。

本文件記錄目前實作的**全部** UI 資訊:文字、字級、字體、玻璃樣式、配色、版面參數。數值皆從原始碼抽取,非估算。

---

## 1. 舞台與縮放

| 項目 | 值 |
|---|---|
| 舞台比例 | 1:1(`aspect-square`) |
| 舞台尺寸 | `h-full max-h-[100vw]`,置中於黑底 |
| 縮放基準 | 舞台層標記 `@container`,**所有尺寸單位皆為 `cqw`** |

`1cqw` = 舞台寬度的 1%。因此換任何解析度的 1:1 螢幕,版面都等比縮放,不需改任何數值。

> 換算範例:`1.5cqw` 在 1080px 舞台 = 16.2px、在 1500px = 22.5px、在 2000px = 30px。

## 2. 按鍵對應

### 影片(數字鍵)

| 鍵 | 檔案 | 內容 | 解析度 | 長度 |
|---|---|---|---|---|
| `1`–`6` | `1.mp4`–`6.mp4` | 森林 | 2160×2160 · 24fps | 15–40s |
| **`7`** | **`7.mp4`** | **城市黃昏(預設)** | 2160×2160 · 24fps | 95.5s(放慢 6 倍 + 來回) |
| `8` | `8.mp4` | 城市夜景 | 2160×2160 · 24fps | 95.5s(放慢 6 倍 + 來回) |

超出範圍的數字鍵(`9` 以上)不作用,維持當前影片。

**開機預設是 `7`**(`DEFAULT_VIDEO_INDEX = 6`,索引從 0 起算)。`7` 與 `8` 是唯二做過「放慢 6 倍 + 來回」的,循環接點的亮度落差是 0 —— 展場會連續播一整天,接縫每隔幾十秒跳一次比畫面本身難看得多。

### 面板(字母鍵,不分大小寫)

| 鍵 | 面板 | 說明 |
|---|---|---|
| 預設 / `A` | 精簡卡片 | 左上 1/4 區塊的單張卡 |
| `S` | 儀表板 | 滿版,現況主卡 + 六格數值 + 三張中卡 + 趨勢 |
| `D` | 詳細版 | 滿版,資訊密度最高,含月相 |
| `F` | 無框版 | 滿版,**無卡片**,細線分區直接壓在影片上 |
| `G` | 面板版 | 滿版,環形 AQI 儀表 + 垂直趨勢列 |

按鍵為**直接選取**,不是切換 —— 重複按同一鍵維持不變。

### 雙螢幕裁切(字母鍵)

| 鍵 | 模式 |
|---|---|
| `L` | 顯示完整畫布的**左半**;再按一次回到一般顯示 |
| `R` | 顯示完整畫布的**右半**;再按一次回到一般顯示 |
| `I` | 切換左下角的狀態角標(顯示這台是 L 還是 R、有沒有連上同步) |
| `W` | 疊出實體窗框的框料(上框、中橫杆、下框、中梃),佈場對位用 |
| `Q` | 切換無濾鏡的備援玻璃;**會同步到另一台** |

**只在視口為直式時生效**(`innerHeight > innerWidth`)。桌面橫式下按 L/R 完全沒有作用,版面與原本一致。

狀態角標**預設隱藏** —— 展場的電視上不該看到它,但佈場時需要確認哪台是哪半、同步有沒有連上,所以留一個按鍵叫出來。**一般模式與裁切模式都會顯示**:同步沒連上時畫面上看不出任何異狀,而一般模式下反而最需要先確認 relay 起來了沒有。

## 2.5 雙螢幕裁切模式

兩台直式電視並排組成一個大畫面,各自開**同一個網址**,L/R 只決定自己看完整畫布的哪一半。

### 做法

裁切模式下,舞台**直接絕對定位**,不包虛擬畫布容器:

```
S = min(200vw, 100dvh)          舞台邊長 = 合併畫布能容納的正方形
height: S                        兩台算法完全相同
top:    calc((100dvh - S) / 2)
left:   calc((200vw - S) / 2)           左半
        calc((200vw - S) / 2 - 100vw)   右半再減一個螢幕寬
```

兩台的尺寸算式一模一樣,只有 `left` 差一個螢幕寬,所以縮放比例必然一致、接縫自然銜接 —— 這比讓左右各自算一次 responsive 可靠得多。裡面的版面尺寸**一行都沒動**。

**曾經用過但已棄用**:「200vw 寬的容器 + 右半 `translateX(-100vw)`」。兩者都會造成面板閃動 —— `transform` 會建立合成層,底下的 `backdrop-filter` 必須相對被變換的空間重新取樣背景,疊上持續變動的影片材質就不穩;`200vw` 也讓圖層面積變成螢幕的兩倍。改用 `left` 直接算位移後,圖層只有舞台本身大小,也沒有 transform。

實測(視口 420×900):

| 模式 | 舞台尺寸 | 舞台相對視口的位置 |
|---|---|---|
| L | 840×840 | `left 0 → right 840`,視口顯示 0–420 |
| R | 840×840 | `left −420 → right 420`,視口顯示的是舞台 420–840 |

兩邊舞台皆為 **840×840**,接縫落在正方形的水平中心。

### 為什麼上限掛在 max-height

`aspect-ratio` 搭 `height: 100%` 時,**`max-width` 不會回頭縮高度** —— 顯式高度會贏,比例反而被破壞(實測會得到 840×900 這種非正方形)。只有 `max-height` 會讓寬度跟著縮。所以裁切模式是把上限從 `100vw` 換成 `200vw`,而不是改用 `max-w-full`。

### UI 不跨接縫

兩台電視中間有實體邊框,任何跨過接縫的卡片都會被切成兩半。所以 S 與 D 在裁切模式下改成**兩半各自成組**:每張卡完整落在自己那半,不跨中線。

做法是把卡片抽成變數(`heroCard`、`metrics`、`aqiCard`…),再由兩套版面分支共用同一份 markup —— 一般顯示維持原本的網格,裁切模式改用 `grid-cols-2`,左右各一欄。外層 padding 左右對稱,所以**中間那道 gap 必然落在接縫上**,不需要量任何像素。

唯一容許跨接縫的是**溫度折線圖**:它本來就是一條連續的線,跨過去反而讀得出「6 小時」的整體走勢(左半 10:00–14:00,右半 16:00–20:00)。實測確認**沒有任何文字**的字身跨過接縫。

四個滿版面板(S、D、F、G)都做了,各自的重點不同:

| 面板 | 原本會被切到的 | 處置 |
|---|---|---|
| S 儀表板 | 三欄網格的分界不在 50% | 改 `grid-cols-2`,左右各一組 |
| D 詳細版 | 同上;空氣品質卡在半個螢幕高度裝不下(溢出 65px) | 四個污染物改 2×2、主要污染物併成一行 |
| F 無框版 | 五格橫條(50% 落在第三格正中)、`1fr/1.55fr` 兩欄(分界在 39%)、置中的更新時間、風雨那排五個欄位 | 橫條每半各自成條、主區改 `grid-cols-2`、更新時間只放左半、風雨拆成上下兩排 |
| G 面板版 | 頂部與底部的五格橫條、三欄網格(分界在 41% 與 79%) | 改左右兩組;十個小指標平均分成每半一條五格 |

G 的內容量在半個螢幕下原本超出約 166px,靠三處壓縮換回來:AQI 環 72% → 44%、六小時直排的圖示與溫度字級縮小(列數不減)、hero 的 flex 比重降低。六小時的資訊一項沒少。

F 與 G 的六格趨勢不必處理:50% 正好是格與格的分界,內容置中不會越界。橫向分隔線與折線同理 —— 跨過邊框會自然接上,反而讀得出整體走勢。

### 濾鏡負擔

裁切模式的舞台面積是一般模式的 **4 倍**(840² vs 420²),每張卡原本又疊了兩層 `backdrop-filter` 在 4K 影片上,會造成面板閃動。實測驗證過成因:關掉模糊就不閃。

但「關掉模糊」不是好答案 —— 少了模糊,卡片只剩壓暗,在亮背景上會顯髒(壓暗改變不了背景很雜,只是把整片變灰)。所以改成從負擔本身下手,**保留模糊**:

| 最佳化 | 做法 | 省下 |
|---|---|---|
| 鏡緣濾鏡關掉 | `[data-crop="1"] .glass::after { backdrop-filter: none }` | 每張卡從兩層濾鏡變一層 |
| 模糊半徑砍半並設上限 | `blur(0.6cqw)` → `blur(min(0.3cqw, 6px))` | 見下 |
| 看不見那半邊不 render | `side` prop,空欄位仍佔位所以版面不變 | 玻璃面積 ~780k → ~407k px²(−48%) |

第三項在卡片還會跨接縫時做不到,是「UI 不跨接縫」之後才成立的。

**為什麼模糊要有像素上限。** 用 `cqw` 表示的半徑會隨螢幕無上限地長大:實機舞台 3840 時 `0.3cqw` = 11.5px,而這套視覺當初是在 840–1080 的舞台上調的(約 2.5–3px)。模糊成本大致是「面積 × 半徑」,實機可見面積已經是開發時的 20 倍,半徑不該再跟著乘 4。6px 是折衷:在 3840 的舞台上仍然是清楚的霧面,工作量約減半。**螢幕小於約 2000px 時 `0.3cqw` 本來就小於 6px,上限不生效,外觀完全不變。**

> 一般模式(非裁切)的模糊仍由各元件的 `backdrop-blur-[0.6–0.75cqw]` 決定,**沒有上限**。直立 4K 電視上一般模式的舞台是 2160²,模糊會到 14px。雙螢幕展場用的是 L/R 裁切模式所以不受影響;若單一 150×150 cm 螢幕也是高解析度而出現閃動,這裡是下一個可調的地方。

**備援**:按 `Q` 切換到完全不用濾鏡的版本(`[data-glass="flat"]`)。若實機仍撐不住,這個版本保證不閃。它不只是把模糊拿掉 —— 底色改成「下限 + 層級差」讓每張卡都有可讀的底,並提亮 `t-caption` / `t-label` 兩階說明字,補回模糊原本抹平背景的作用。

### 畫面邊緣

畫布是 1:1,兩台直式螢幕合併後通常不是正方形,所以左右外緣一定會有黑邊,接縫處則完整銜接。這是 1:1 設計在非正方形合併區域上的必然結果。

**實際展場配置(兩台 65 吋 4K 電視直立並排),已在瀏覽器實測:**

| 項目 | 值 |
|---|---|
| 每台視口 | 2160 × 3840(4K 面板直立,dPR 1) |
| 合併畫布寬 | 4320 |
| 舞台 | **3840 × 3840** |
| 外緣黑邊 | 每側 **240px** |
| `1cqw` | **38.4px** |

換算成實體尺寸:65 吋 16:9 面板直立後約 809 × 1439 mm,兩台並排 1618 mm 寬。舞台是 1439 × 1439 mm,**左右外緣各約 89 mm 黑邊**。

片源是 2160×2160,舞台 3840 → 會被放大約 1.78 倍。這無法避免:原始素材只有 2160 條垂直掃描線,2160 已經是能取出的最大正方形。霧林這類柔性內容放大後的表現還算寬容。

**負擔的量級**:每台可見 2160×3840 = 8.3 MP,是開發時測試視口(460×900)的 **20 倍**。模糊半徑若不設上限會變成 11.5px(開發時是 2.7px)。所以裁切模式的模糊加了像素上限,見下。

## 5. 玻璃系統

定義於 `src/app/globals.css` 的 `.glass`,四個有卡片的面板共用。分三個層級,只覆寫變數,本體規則不重複。

### 層級變數

| 變數 | `glass-hero` | `.glass`(base) | `glass-quiet` | 作用 |
|---|---|---|---|---|
| `--glass-tint` | 0.15 | 0.10 | 0.06 | 面的白色底調 |
| `--glass-shade` | 0.13 | 0.10 | 0.035 | 底色壓暗 |
| `--glass-glow` | 0.16 | 0.12 | 0.07 | 邊緣往內的柔光 |
| `--glass-edge` | 0.5 | 0.33 | 0.19 | 細光邊亮度 |
| `--glass-lift` | 0.24 | 0.16 | 0.08 | 外投影濃度 |
| `--glass-sat` | 1.5 | 1.4 | 1.25 | 鏡緣飽和度 |
| `--glass-bright` | 1.5 | 1.4 | 1.22 | 鏡緣提亮 |
| `--glass-veil` | 0.12 | 0.09 | 0.05 | 鏡緣白紗 |

**`--glass-shade` 必須跟著層級走**。曾經它是固定值(`bg-black/12`),導致 quiet 卡「6% 白對 12% 黑」淨變暗,在畫面上呈現為暗塊。

### 組成層

1. **底色** `background-color: rgb(0 0 0 / var(--glass-shade))`
2. **面漸層** `linear-gradient(158deg, 白 tint → 白 tint×0.28 @42% → 黑 shade×0.45)` — 左上受光、右下沉下去
3. **內側柔光** 兩道 `inset box-shadow`(左上 `0.2cqw/0.9cqw` 強、右下 `-0.26cqw/1cqw` 弱)
4. **上緣高光** `inset 0 0.06cqw 0`,亮度為 `edge × 0.3`
5. **外投影** `0 0.35cqw 1.3cqw`,濃度 `--glass-lift`
6. **細光邊** `::before` — hairline `padding: 0.05cqw`,漸層 138°,高光集中在 7% 與 92% 兩處
7. **鏡緣** `::after` — 見下

> 柔光刻意用 `inset box-shadow` 而非模糊的偽元素:絕對定位的偽元素會疊在文字之上糊到字,`inset shadow` 屬於背景層,一定畫在內容之下。

### 鏡緣(邊緣對背景的回應)

```css
.glass::after {
  background: rgb(255 255 255 / var(--glass-veil));
  backdrop-filter: blur(0.7cqw) saturate(var(--glass-sat)) brightness(var(--glass-bright));
  mask-image:
    linear-gradient(138deg, #000 0% 16%, rgb(0 0 0/0.18) 36% 64%, #000 84% 100%),
    linear-gradient(to right,  #000, transparent 2.6cqw),
    linear-gradient(to left,   #000, transparent 2.6cqw),
    linear-gradient(to bottom, #000, transparent 2.6cqw),
    linear-gradient(to top,    #000, transparent 2.6cqw);
  mask-composite: intersect, add, add, add;
}
```

邊緣對背景做濾鏡而非塗白,所以**背景一變邊角就跟著變**。三個實作要點:

- **必須帶 `blur`**。父層的 `backdrop-blur` 會建立 backdrop root,`::after` 自己的 `backdrop-filter` 濾的是那層之外的原始影片而非已霧化的底;少了 blur,鏡緣會顯示沒霧化、較暗的影片,在明亮霧面旁變成**一圈暗帶**。
- **提亮為主、加濃為輔**。飽和度拉太高會壓低明度,結果變暗。另加白紗當下限,確保鏡緣永遠比內部亮。
- **四邊淡出取聯集,再與對角遮罩取交集**。四邊淡出讓內側沒有硬切;對角遮罩讓反光只在對角兩端明顯(中段 18%),不是均勻一整圈。

### 各面板卡片參數

| 面板 | 圓角 | 內距 | 模糊 | 外層 padding |
|---|---|---|---|---|
| A 精簡卡片 | `2.2cqw` | `3.6cqw` | `0.75cqw` | `3cqw`(定位容器) |
| S 儀表板 | `1.7cqw` | `2.1cqw` | `0.65cqw` | `4cqw`,gap `1.6cqw` |
| D 詳細版 | `1.6cqw` | `1.95cqw` | `0.6cqw` | `3.5cqw`,gap `1.4cqw` |
| G 面板版 | `1.7cqw` | 依卡片 `1.8–2.5cqw` | `0.6cqw` | `4cqw`,gap `1.5cqw` |
| F 無框版 | — | — | — | `px/py 6cqw`,底 `bg-black/30` |

F 無框版沒有卡片,靠整面 `bg-black/30` 讓文字站得住,分區用 `divide-white/20` 細線。

### 播放架構(`VideoBackground.tsx`)

六個 `<video>` 元素同時掛載,只有顯示中的那支在播,其餘 `pause()` 但**保留已下載的緩衝**。三個要點:

1. **`src` 一律在 effect 裡指定**,不寫進 SSR HTML。寫進去的話瀏覽器會在解析階段就開抓影片,跟 JS chunks 搶頻寬(實測讓 hydration 延後 40 秒)。
2. **依序預載** —— 載完一支(`canplaythrough`)才開始下一支,避免背景預載把開場的頻寬吃光。
3. **`play()` 在 `visibilitychange` 時重試** —— `play()` 是一次性的,不像 `autoPlay` 屬性會自動重試;分頁在背景時會被拒絕,展示螢幕不能停在靜止首格。

切換影片**不會重新下載**(實測多次切換 0 個新請求)。這點重要,因為 GitHub Pages 只給 `Cache-Control: max-age=600`。

### 已知取捨

影片全為 16:9,舞台是 1:1,`object-fit: cover` 會裁掉中間以外約 44% 的畫面寬度。每一幀解 8.29M 像素、只用 4.67M。**尚未重壓** —— 是否需要取決於展示機的實測掉幀率。

## 9.5 跨裝置同步

兩台電視各自開同一個網址,用 **WebSocket** 讓場景與影片時間一致。

刻意**不用 localStorage** —— 那是同一瀏覽器同一 origin 內共享,跨裝置無效。

### 兩條通道

| 通道 | 範圍 | 需要伺服器 | https 可用 |
|---|---|---|---|
| `BroadcastChannel` | 同一個瀏覽器裡的視窗 | 否 | **是** |
| WebSocket relay | 不同機器 | 是 | 否(混合內容) |

**一台電腦推兩台螢幕、開兩個視窗的情況靠 BroadcastChannel 就夠了**,不必跑 relay,而且在 GitHub Pages 上照樣會同步 —— 這是先前只有 WebSocket 時做不到的(Pages 是 https,連不上 `ws://`)。

兩條同時開著,訊息往兩邊送。`BroadcastChannel` 不會把訊息送回發送端自己,所以不必額外防回彈;跨通道的回彈由 `appliedRef` 擋掉。收訊處理兩條共用同一個 `handleMessage`,包含「連上未滿 3 秒不回答 hello」那條規則。

狀態角標(`I`)分開顯示兩條:`relay on/off` 與 `local on/off`。

仍然**不用 localStorage** —— 它跨裝置無效,而且要靠 storage 事件輪替,語意比 `BroadcastChannel` 髒得多。

### 伺服器

`server/sync-server.mjs`,一個無狀態的廣播中繼:收到什麼就轉給其他連線,自己不解讀內容。

```bash
npm run sync          # 預設 8787
PORT=9000 npm run sync
```

位址的決定順序:

| 順序 | 來源 | 用途 |
|---|---|---|
| 1 | 網址參數 `?sync=ws://…` | 展場現場臨時指定,不必重新建置 |
| 2 | `NEXT_PUBLIC_SYNC_URL` | 建置時固定 |
| 3 | `ws://<頁面所在主機>:8787` | 預設 |

所以兩台電視只要從同一台展場機器開頁面,**零設定即可運作**。

**連不上時整站照常運作**(單機模式),只是不同步 —— 靜態部署不會因為沒有 sync server 而壞掉。斷線後以 1s → 10s 的退避重連,relay 重新起來會自己接回去。

### 展場一定要注意的兩件事

**一、relay 必須是開著的。** 沒開的時候畫面上看不出任何異狀,兩台就這樣各走各的。按 `I` 叫出狀態角標確認 —— `sync on` 是綠的、`off` 是紅的。角標在一般模式與裁切模式都會顯示(裁切模式另外顯示這台是 L 還是 R)。

**二、雙螢幕請從本機以 http 提供頁面,不要開 GitHub Pages 那個網址。** https 頁面連 `ws://` 會被瀏覽器當成混合內容擋掉,而 GitHub Pages 只能給靜態檔、架不了 WebSocket server。那份部署是預覽與分享用的,雙螢幕同步在上面不可能運作。

> 停 relay 時注意:`npm run sync` 底下還有一個 node 子行程,只結束 npm 的包裝行程時 8787 仍會被佔著。終端機按 Ctrl-C 會正常結束,用工具強制結束則要確認埠真的釋放了。

### 訊息協定

| 型別 | 誰發 | 內容 |
|---|---|---|
| `hello` | 剛連上的那台 | 詢問現在的場景 |
| `scene` | 任一台(場景變動時) | `{ videoIndex, panel }` |
| `clock` | **左半那台**,每 400ms | `{ videoIndex, time }` |

### 三個必要的防護

**1. 掛載時不廣播。** `appliedRef` 初始值設成本地初始場景,所以剛載入的那台不會廣播自己的預設值。否則任何一台重新載入(斷電、瀏覽器重啟)都會把還在正常播放的另一台**重設回影片 1 + 精簡卡片**。

**0. 同步哪些、不同步哪些。** 場景是 `{ videoIndex, panel, flatGlass }`。

`flatGlass`（`Q`）要同步 —— 兩半的玻璃質感不一致會很明顯。`display`（`L`／`R`）**刻意不同步**：那是每台自己看哪一半，同步過去等於兩台看同一半。`showStatus`（`I`）也不同步，它是每台各自的佈場工具。

收訊時 `flatGlass` 用 `=== true` 取值，舊版本的 client 沒送這個欄位也不會壞。

**2. 剛加入的不回答 hello。** 只有連上超過 3 秒的那台才回答。兩台同時開機時都會發 `hello`,若雙方都回答就會**互換場景**,變成各自不同步。

**3. 遠端套用的不再廣播。** 收到 `scene` 時記下 payload,本地廣播前比對,相同就跳過,避免兩台互相回彈。

### 影片時間同步

左半那台是時間來源,右半跟隨。校正在 `VideoBackground.tsx`,**漸進而非硬跳**:

| 偏差 | 動作 |
|---|---|
| > 0.5s | 硬 `seek`(長時間追趕比跳一次更難看) |
| 0.06 – 0.5s | `playbackRate` 0.97 / 1.03 讓它自己收斂 |
| ≤ 0.06s | `playbackRate` 歸 1 |

另外處理兩件事:

- **傳輸延遲補償** — 目標時間加上訊息在網路上花掉的時間(`performance.now() - sentAt`)
- **loop 邊界** — 影片是循環的,跨越循環點時原始差值會接近整支長度,換算成較短的那一側

沒有時間來源時 `playbackRate` 主動歸 1,否則會停在上次的校正值。發布端只在 `!paused` 時送出,不發布停住的時間。

實測(以外部 WS client 假扮左螢幕發送已知時間):

| 送出 | 結果 |
|---|---|
| 大偏差 `time=20.0` | `seeking → seeked` 到 20.01 ✓ |
| 落後 0.2s | `ratechange → 1.03` ✓ |
| 超前 0.2s | `ratechange → 0.97` ✓ |
| 同步 | `ratechange → 1` ✓ |

左半那台發布間隔實測平均 **400ms**,與設定值一致。

## 11. 自訂推導的指標

以下三項 API 沒有,是自訂邏輯。

### 舒適度(`comfortLabel`)

以體感溫度為主,濕度高時往「悶」修正。

| 條件 | 結果 |
|---|---|
| 體感 ≥ 35 | 悶熱 |
| ≥ 30 | 濕度 ≥ 70 → 偏悶熱,否則偏熱 |
| ≥ 26 | 濕度 ≥ 80 → 微悶,否則溫暖 |
| ≥ 20 | 舒適 |
| ≥ 15 | 微涼 |
| ≥ 10 | 偏涼 |
| < 10 | 寒冷 |

### 體感趨勢(`feelsTrendLabel`)

比較現在與 3 小時後的體感溫度:差 ≥ +1.5 → 上升、≤ −1.5 → 下降、其餘 → 穩定。

### 蒸發感(`evaporationLabel`)

`index = ((100 − 濕度) / 100) × (1 + 風速 / 25) × (溫度 / 28)`

≥ 0.75 → 強、≥ 0.35 → 中等、< 0.35 → 弱。**無官方定義**,純自訂指標。

### 空氣狀態(`airStateLabel`)

比 AQI 分級再粗一階:≤ 50 清新、≤ 100 普通、≤ 150 稍差、> 150 混濁。

### 月相(`moon.ts`)

API 沒有月相,以 **2000-01-06 18:14 UTC 新月**為基準,除以朔望月 **29.530588853** 天取餘數。

```
illumination = (1 − cos(2π × 月齡 / 29.530588853)) / 2
waxing = 月齡 < 朔望月 / 2
```

已對照已知日期驗證:新月 0.1%、滿月 99.8%、上下弦約 45% 且盈虧方向正確。

**限制**:平均朔望月模型,未計入月球軌道離心率,上下弦會算出約 45% 而非精確 50%,誤差約半天。展示用足夠,非天文級精度。

## 12. 載入閘門

開場那幾秒影片還在抓、天氣還沒回來,面板會先以骨架狀態出現再跳成實際數值,展場看起來像出錯。所以蓋一層整片黑幕,等兩件事都成立才淡出(900ms):

1. 顯示中的影片觸發 `playing` —— 用 `playing` 而不是 `canplaythrough`,因為前者是真的開始出畫格,後者只保證資料夠。黑幕收掉的瞬間底下一定已經是動的影像。
2. 天氣有結果(拿到資料或確定失敗)。

**逾時 10 秒無條件放行。** 自動播放被擋或影片抓不到時 `playing` 永遠不會來,沒有逾時的話展示螢幕會整晚停在黑幕上 —— 寧可露出未完成的畫面,也不能全黑。

黑幕蓋住整個視窗(含 1:1 舞台外的黑邊),淡出後留在 DOM 裡設 `opacity: 0`,不卸載。切換影片不會讓它回來(只回報第一次)。

## 13. 影片編碼

**森林六支**(`1`–`6`):

| | 原始 | 現在 |
|---|---|---|
| 解析度 | 3840×2160 | **2160×2160** |
| 每格像素 | 8.29 MP | 4.67 MP(−44%) |
| 位元率 | 8.2–10.9 Mbps | 4.6–9.0 Mbps |
| 六支合計 | 189 MB | **124 MB**(−34%) |
| 編碼 | H.264 Main | H.264 High |

**城市兩支**(`7`、`8`):來源都是 3840×2160 / 24fps / 8 秒,和森林那批同等級,壓縮設定也完全相同。

兩支的天色都在這 8 秒內持續改變,直接循環會看得出來跳:

| | 天色 | 首格 | 尾格 | 單向循環落差 |
|---|---|---|---|---|
| `7` 黃昏 | 轉暗 | 112 | 103 | **9** |
| `8` 夜景 | 轉亮 | 40 | 84 | **44** |

(森林那六支是 0–2。)

兩支都處理成**放慢 6 倍 + 來回播放**,各 95.5 秒、44.8 / 50.2 MB:

```
[0:v]crop=2160:2160:840:0,split[c1][c2];
[c1]trim=start_frame=1,setpts=6*(PTS-STARTPTS)[f];
[c2]reverse,trim=start_frame=1,setpts=6*(PTS-STARTPTS)[r];
[f][r]concat=n=2:v=1[out]
```

三個要點:

**兩段各砍掉第一格。** 不砍的話接點與循環點各會多一格重複:正放末格接反放首格是同一格、反放末格接正放首格也是同一格。砍掉之後 正放`1…N-1` → 反放`N-2…0` → 循環回 `1`,兩處都連續。

**沒有補幀 —— 而且是量過才決定的。** 放慢 6 倍等於每格停留 250ms,獨立畫面只剩 **4 格/秒**,理論上是會看到階梯的臨界點。但實測「每一步」的變化分布:

| 每步變化超過 | `7` | `8` |
|---|---|---|
| 5 | 0.49% | 0.85% |
| 20 | 0.20% | 0.27% |
| 100 | 0.011% | 0.007% |

也就是 **99.5% 以上的畫面幾乎靜止**(每步平均差 0.38 / 0.69),快速變化的只有零星的城市燈點 —— 那在夜景裡本來就是閃爍感,不會被看成階梯。單點最大變化雖然到 165,但那是單一像素的燈。所以 `minterpolate` 的形變風險與編碼成本都不值得換。

**實測結果**:循環點與轉折點的亮度落差都是 **0**(原本 9);鏡像位置(`t` 與 `D-t`)的畫面平均差 0.49–0.63,而不對稱位置是 8.39 —— 來回結構正確。

**實測結果**:兩支的循環點與轉折點亮度落差都是 **0**;鏡像位置(`t` 與 `D-t`)的畫面平均差 `7` 是 0.49–0.63、`8` 是 0.83–0.89,而不對稱位置分別是 8.39 與 27.54 —— 來回結構正確。

> 倒放會讓畫面動態反向。這兩支都是遠景城市、主要動態是雲與光線變化,看不出來;若換成有明顯方向性動態的素材(人、車近景)就不適用。
>
> `8` 的相鄰格平均差是 0.60(`7` 與森林是 0.34)—— 動態稍快一些但仍遠低於會產生可見跳動的程度,所以同樣不補幀。

## 14. 影片預載排程

六支影片全部掛在 DOM 上,只有顯示中的那支播放,其餘暫停但保留緩衝,所以切換是即時的。問題在於**什麼時候去抓那五支**。

原本是鏈式的:某支 `canplaythrough` 就指定下一支的 `src`。看起來是「載完一支才載下一支」,實際不是 —— `canplaythrough` 只表示「以目前速率估計能播完」,不必等整支下載完就觸發。實測六支在 **1.2 秒內全部開始下載**(527/663/768/888/1080/1191ms),等於開場同時有六個下載與六個解多工器在跑,而合成器正在對舞台做 `backdrop-filter`。

這就是前幾秒偶爾閃動的來源,也解釋了為什麼**不是每次都閃**:檔案在不在快取裡,決定了負擔差多少。

改成時間排程:

| 常數 | 值 | 作用 |
|---|---|---|
| `PRELOAD_START_MS` | 6000 | 開始播之後,先讓那支獨佔資源這麼久 |
| `PRELOAD_GAP_MS` | 4000 | 之後每多載一支的間隔 |
| `PRELOAD_FALLBACK_MS` | 12000 | 從未開始播時,預載仍然啟動 |

逾時保險是必要的:自動播放被擋的話 `playing` 永遠不會來,少了它就再也不會預載任何一支,之後每次切換都得從頭抓。

切換仍然是即時的 —— 真的切到還沒載的那支時,`activeIndex` 的 effect 會當場指定 `src`。

## 15. 實體窗框與 UI 安全區

展場是兩台 65 吋電視直立並排,前方再罩一扇實體窗框。

### 框與螢幕的關係

**框比螢幕窄、比螢幕高**,這決定了一切:

```
      ┌──────────────┐  ← 窗框 1420 × 1500
    ┌─┼──────────────┼─┐
    │ │              │ │  ← 兩台電視合併 1618.8 × 1438.9
    └─┼──────────────┼─┘
      └──────────────┘
```

| | 值 |
|---|---|
| 單台面板(65 吋 16:9 直立) | 809.4 × 1438.9 mm |
| 兩台合併顯示區 | **1618.8 × 1438.9 mm** |
| 窗框 | 1420 × 1500 mm,兩軸置中 |
| 框相對螢幕 | x **+99.4**,y **−30.5**(框比螢幕高) |

換算成佔舞台的百分比(舞台 = 1:1,邊長取顯示區的短邊即高,水平置中):

| 框料 | 位置 | 說明 |
|---|---|---|
| 上框 | **−2.1% → 2.0%** | 大半在螢幕上方,只有 2% 露出 |
| 上段玻璃 | 2.0% → 70.2% | |
| **中橫杆** | **70.2% → 75.7%** | **唯一真正橫過畫面的橫向框料** |
| 下段玻璃 | 75.7% → 98.0% | |
| 下框 | **98.0% → 102.1%** | 大半在螢幕下方 |
| 左右邊料 | 0 → 0.66%,99.34% → 100% | 電視比框寬,蓋掉的正好是 1:1 舞台的黑邊 |
| 中梃 | 48.61% → 51.39% | 落在正中線,也就是兩台電視的接縫 |

**先前假設「框的開口就是舞台」是錯的** —— 那會把上下框當成擋住畫面的東西,白白讓出高度,UI 也因此縮得比需要的小。實際上上下框幾乎都在畫面外,而左右邊料只蓋掉黑邊。

框料尺寸集中在 `src/lib/frame.ts` 的 `FRAME`,面板尺寸由對角線算出;實際丈量不同時改那裡即可,安全區與三列切分會自己重算。

> 圖上的 1380 讀作「上段玻璃頂到下段玻璃底」,由此推得中橫杆 80、上下框各 60。這是唯一靠推論得出的部分,現場請用 `W` 對位確認。

### 只有 UI 內縮,影片維持滿版

景色從框料後面延續過去正是窗景該有的樣子,被擋住不損失資訊;文字與卡片被切掉才是真的看不到。所以影片鋪滿整個舞台,只有面板層退到安全區內。

### 安全區

一個 1:1 的正方形,讓開所有真的會擋到畫面的框料:

| | 值 |
|---|---|
| 邊長 | 舞台的 **95.90%** |
| 位置 | `top: 2.05%`,水平置中 |
| 裁切時每半長寬比 | **0.50** —— 正好是裁切版面原本設計的比例 |

縱向受限於上框下緣與下框上緣,橫向受限於左右邊料;縱向比較緊,所以邊長由它決定。**因為仍然是 1:1,四個面板的版面比例一格未動。**

A 精簡卡片不進安全區,見下。

### 中橫杆:一道橫向的接縫

中橫杆是唯一真正橫過畫面的框料,字落在那一段就等於消失。處理方式和垂直接縫(中梃、兩台電視之間)完全同一套:**版面切成「上半段 / 橫杆(留空)/ 下半段」三列**。

列高由 `railRows(padCqw)` 算出 —— 各面板外層 padding 不同,而 `cqw` 是安全區寬度的 1%、安全區又是正方形,所以 padding 佔內容區高度的比例就等於那個 cqw 數字:

| 面板 | padding | 下半段放什麼 |
|---|---|---|
| S | 4cqw | 趨勢卡 + 更新時間 |
| D | 3.5cqw | 趨勢卡 + 更新時間 |
| F | 6cqw | 六小時趨勢 + 更新時間 |
| G | 4cqw | 兩欄各自的五格指標;左欄再帶上降雨量 |

S、D、F 本來就以趨勢作結,G 的兩欄本來就都以五格指標作結,所以這個切分是順著原本的結構走的,不是硬切。

為了讓上半段裝得下,裁切模式收了三處尺寸:F 的趨勢圖示 6.5→3.5cqw、溫度 3→1.9cqw;G 的 AQI 環 44%→33%、日照弧 68%→56%、六小時直排列距歸零。**列數與資訊一項沒少。**

實測四個面板在裁切模式下:橫杆淨空、卡內無溢出、無文字跨接縫。

兩種模式共用同一套三列切分,所以單一螢幕擺在同一扇框後面也成立。

### 趨勢卡拆成左右兩張

原則是**黃色框料上不出現任何文字或卡片,只有折線允許跨過去**。

實測後只有一處違反:S 與 D 的趨勢卡是滿版的,卡片本身跨過中梃(文字沒有 —— 先前量到的是元素框,不是字身)。

處理方式:趨勢卡拆成左右兩張,間隙**正好等於中梃寬**(`MULLION_CQW`,約 2.90cqw)。折線則兩張卡都畫「完整的六個點」,只是 x 起點差一張卡寬,各自被自己的卡片裁掉 —— 拼起來就是一條線,**唯一的斷點正好被實體中梃遮住**。

座標由 `splitTrendX(面板內距, 卡片內距)` 算出。不能當成「均分六欄」:每張卡內部是三欄、還有自己的內距,和整段均分不一樣。折線容器用負 margin 撐出卡片內距,線才畫得到卡片邊緣。

兩張卡的內部結構必須一模一樣,折線高度才對得齊 —— 所以右邊留一個 `invisible` 的標題佔位。

中橫杆以下只有約 19% 的高度,所以裁切版把行距與線高一起收緊(S 的線 6→3.5cqw、D 5→3cqw,圖示與行距同步縮小),並把「資料更新時間」移到面板底部的內距裡(仍在下段玻璃內),整列讓給趨勢卡。**列數與資訊一項沒少。**

### 一般模式也用同一套框後版面

先前只讓裁切模式(L/R)避開框料,一般模式沿用原本的多欄網格 —— 那是錯的,**實體窗框一直都在**。實測一般模式:中橫杆把整條折線蓋掉、下框吃掉更新時間、中梃剖開每一張卡。

所以 `crop` 這個 prop 的意思改成「**框後面的版面**」,兩種模式一律為 true。真正只有雙螢幕才需要的是 `side`(另一半不 render),那個維持只在裁切時給。

### 驗證方式

用字身(`Range.getClientRects`)而非元素框去撞六塊框料 —— 靠左或置中的文字,元素框常常是整欄寬,用它會得到一堆假警報。卡片則用外框。

疊圖用**不透明**的實色 —— 半透明會讓人誤判「這樣應該還看得到」,實色直接呈現「這一塊就是看不到」。

實測 **5 個面板 × 2 種模式 = 10 種組合**:六塊黃色框料全部淨空,且沒有任何內容被卡片裁掉。

載入畫面的「載入中」也移離中梃(水平 30%)—— 置中的話它正好躲在框料後面。

### A 精簡卡片不進安全區

A 本來就是一張靠左上的小卡,而安全區是水平置中的 —— 放進去會被推到畫面正中央,失去「窗角上的一張卡」那個構圖。所以 A 直接貼著上段玻璃的左上角,尺寸仍以舞台為基準。

容器佔舞台一半,扣掉 `3cqw` 內距後右緣落在 47%,而中梃從 48.61% 才開始,所以卡片不會碰到它。

### 對位工具

按 `W` 把框料疊在畫面上(上框、中橫杆、下框、中梃),確認 UI 真的落在玻璃區內。展場不該看到,預設隱藏。
