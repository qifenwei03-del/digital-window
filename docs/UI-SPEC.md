# Digital Window — UI 規格

寶鋪知行案 C 區數位窗景。1:1 展示螢幕(實體 150 × 150 cm),影片背景 + 可切換的天氣面板。

本文件記錄目前實作的**全部** UI 資訊:文字、字級、字體、玻璃樣式、配色、版面參數。數值皆從原始碼抽取,非估算。

---

## 1. 舞台與縮放

| 項目 | 值 |
|---|---|
| 舞台比例 | 1:1(`aspect-square`) |
| 舞台尺寸 | `h-full max-h-[100vw]`,置中於黑底 |
| 縮放基準 | 舞台層標記 `@container`,**所有尺寸單位皆為 `cqw`** |

`1cqw` = 舞台寬度的 1%。因此換任何解析度的 1:1 螢幕,版面都等比縮放,不需改任何數值。

> 換算範例:`1.5cqw` 在 1080px 舞台 = 16.2px、在 1500px = 22.5px、在 2000px = 30px。

## 2.5 雙螢幕裁切模式

兩台直式電視並排組成一個大畫面,各自開**同一個網址**,L/R 只決定自己看完整畫布的哪一半。

### 做法

在原本的 `main` 外面包一層「虛擬畫布」:

| | 一般顯示 | 裁切模式 |
|---|---|---|
| 虛擬畫布寬 | `100%` | **`200vw`**(兩台螢幕合併寬度) |
| `transform` | 無 | 右半為 `translateX(-100vw)` |
| 舞台高度上限 | `100vw` | **`200vw`** |
| 外層 | `overflow: hidden` | 同左 |

裡面的版面**一行都沒動**,所以兩邊的縮放比例必然一致 —— 這比讓左右各自算一次 responsive 可靠得多。

實測(視口 420×900):

| 模式 | 舞台尺寸 | 舞台相對視口的位置 |
|---|---|---|
| L | 840×840 | `left 0 → right 840`,視口顯示 0–420 |
| R | 840×840 | `left −420 → right 420`,視口顯示的是舞台 420–840 |

兩邊舞台皆為 **840×840**,接縫落在正方形的水平中心。

### 為什麼上限掛在 max-height

`aspect-ratio` 搭 `height: 100%` 時,**`max-width` 不會回頭縮高度** —— 顯式高度會贏,比例反而被破壞(實測會得到 840×900 這種非正方形)。只有 `max-height` 會讓寬度跟著縮。所以裁切模式是把上限從 `100vw` 換成 `200vw`,而不是改用 `max-w-full`。

### 畫面邊緣

畫布是 1:1,兩台直式螢幕合併後通常不是正方形。以 1080×1920 的面板為例,合併區域 2160×1920,舞台為 1920×1920 置中 → **左右外緣各留約 120px 黑邊**,接縫處則完整銜接。這是 1:1 設計在非正方形合併區域上的必然結果。

## 5. 玻璃系統

定義於 `src/app/globals.css` 的 `.glass`,四個有卡片的面板共用。分三個層級,只覆寫變數,本體規則不重複。

### 層級變數

| 變數 | `glass-hero` | `.glass`(base) | `glass-quiet` | 作用 |
|---|---|---|---|---|
| `--glass-tint` | 0.15 | 0.10 | 0.06 | 面的白色底調 |
| `--glass-shade` | 0.13 | 0.10 | 0.035 | 底色壓暗 |
| `--glass-glow` | 0.16 | 0.12 | 0.07 | 邊緣往內的柔光 |
| `--glass-edge` | 0.5 | 0.33 | 0.19 | 細光邊亮度 |
| `--glass-lift` | 0.24 | 0.16 | 0.08 | 外投影濃度 |
| `--glass-sat` | 1.5 | 1.4 | 1.25 | 鏡緣飽和度 |
| `--glass-bright` | 1.5 | 1.4 | 1.22 | 鏡緣提亮 |
| `--glass-veil` | 0.12 | 0.09 | 0.05 | 鏡緣白紗 |

**`--glass-shade` 必須跟著層級走**。曾經它是固定值(`bg-black/12`),導致 quiet 卡「6% 白對 12% 黑」淨變暗,在畫面上呈現為暗塊。

### 組成層

1. **底色** `background-color: rgb(0 0 0 / var(--glass-shade))`
2. **面漸層** `linear-gradient(158deg, 白 tint → 白 tint×0.28 @42% → 黑 shade×0.45)` — 左上受光、右下沉下去
3. **內側柔光** 兩道 `inset box-shadow`(左上 `0.2cqw/0.9cqw` 強、右下 `-0.26cqw/1cqw` 弱)
4. **上緣高光** `inset 0 0.06cqw 0`,亮度為 `edge × 0.3`
5. **外投影** `0 0.35cqw 1.3cqw`,濃度 `--glass-lift`
6. **細光邊** `::before` — hairline `padding: 0.05cqw`,漸層 138°,高光集中在 7% 與 92% 兩處
7. **鏡緣** `::after` — 見下

> 柔光刻意用 `inset box-shadow` 而非模糊的偽元素:絕對定位的偽元素會疊在文字之上糊到字,`inset shadow` 屬於背景層,一定畫在內容之下。

### 鏡緣(邊緣對背景的回應)

```css
.glass::after {
  background: rgb(255 255 255 / var(--glass-veil));
  backdrop-filter: blur(0.7cqw) saturate(var(--glass-sat)) brightness(var(--glass-bright));
  mask-image:
    linear-gradient(138deg, #000 0% 16%, rgb(0 0 0/0.18) 36% 64%, #000 84% 100%),
    linear-gradient(to right,  #000, transparent 2.6cqw),
    linear-gradient(to left,   #000, transparent 2.6cqw),
    linear-gradient(to bottom, #000, transparent 2.6cqw),
    linear-gradient(to top,    #000, transparent 2.6cqw);
  mask-composite: intersect, add, add, add;
}
```

邊緣對背景做濾鏡而非塗白,所以**背景一變邊角就跟著變**。三個實作要點:

- **必須帶 `blur`**。父層的 `backdrop-blur` 會建立 backdrop root,`::after` 自己的 `backdrop-filter` 濾的是那層之外的原始影片而非已霧化的底;少了 blur,鏡緣會顯示沒霧化、較暗的影片,在明亮霧面旁變成**一圈暗帶**。
- **提亮為主、加濃為輔**。飽和度拉太高會壓低明度,結果變暗。另加白紗當下限,確保鏡緣永遠比內部亮。
- **四邊淡出取聯集,再與對角遮罩取交集**。四邊淡出讓內側沒有硬切;對角遮罩讓反光只在對角兩端明顯(中段 18%),不是均勻一整圈。

### 播放架構(`VideoBackground.tsx`)

六個 `<video>` 元素同時掛載,只有顯示中的那支在播,其餘 `pause()` 但**保留已下載的緩衝**。三個要點:

1. **`src` 一律在 effect 裡指定**,不寫進 SSR HTML。寫進去的話瀏覽器會在解析階段就開抓影片,跟 JS chunks 搶頻寬(實測讓 hydration 延後 40 秒)。
2. **依序預載** —— 載完一支(`canplaythrough`)才開始下一支,避免背景預載把開場的頻寬吃光。
3. **`play()` 在 `visibilitychange` 時重試** —— `play()` 是一次性的,不像 `autoPlay` 屬性會自動重試;分頁在背景時會被拒絕,展示螢幕不能停在靜止首格。

切換影片**不會重新下載**(實測多次切換 0 個新請求)。這點重要,因為 GitHub Pages 只給 `Cache-Control: max-age=600`。

### 已知取捨

影片全為 16:9,舞台是 1:1,`object-fit: cover` 會裁掉中間以外約 44% 的畫面寬度。每一幀解 8.29M 像素、只用 4.67M。**尚未重壓** —— 是否需要取決於展示機的實測掉幀率。

## 9.5 跨裝置同步

兩台電視各自開同一個網址,用 **WebSocket** 讓場景與影片時間一致。

刻意**不用 localStorage** —— 那是同一瀏覽器同一 origin 內共享,跨裝置無效。

### 伺服器

`server/sync-server.mjs`,一個無狀態的廣播中繼:收到什麼就轉給其他連線,自己不解讀內容。

```bash
npm run sync          # 預設 8787
PORT=9000 npm run sync
```

前端預設連 `ws://<頁面所在主機>:8787`,所以兩台電視只要從同一台展場機器開頁面,**零設定即可運作**。要指定別的位址就用 `NEXT_PUBLIC_SYNC_URL` 建置。

**連不上時整站照常運作**(單機模式),只是不同步 —— 所以 GitHub Pages 那份靜態部署不會因為沒有 sync server 而壞掉。斷線後以 1s → 10s 的退避重連。

### 訊息協定

| 型別 | 誰發 | 內容 |
|---|---|---|
| `hello` | 剛連上的那台 | 詢問現在的場景 |
| `scene` | 任一台(場景變動時) | `{ videoIndex, panel }` |
| `clock` | **左半那台**,每 400ms | `{ videoIndex, time }` |

### 三個必要的防護

**1. 掛載時不廣播。** `appliedRef` 初始值設成本地初始場景,所以剛載入的那台不會廣播自己的預設值。否則任何一台重新載入(斷電、瀏覽器重啟)都會把還在正常播放的另一台**重設回影片 1 + 精簡卡片**。

**2. 剛加入的不回答 hello。** 只有連上超過 3 秒的那台才回答。兩台同時開機時都會發 `hello`,若雙方都回答就會**互換場景**,變成各自不同步。

**3. 遠端套用的不再廣播。** 收到 `scene` 時記下 payload,本地廣播前比對,相同就跳過,避免兩台互相回彈。

### 影片時間同步

左半那台是時間來源,右半跟隨。校正在 `VideoBackground.tsx`,**漸進而非硬跳**:

| 偏差 | 動作 |
|---|---|
| > 0.5s | 硬 `seek`(長時間追趕比跳一次更難看) |
| 0.06 – 0.5s | `playbackRate` 0.97 / 1.03 讓它自己收斂 |
| ≤ 0.06s | `playbackRate` 歸 1 |

另外處理兩件事:

- **傳輸延遲補償** — 目標時間加上訊息在網路上花掉的時間(`performance.now() - sentAt`)
- **loop 邊界** — 影片是循環的,跨越循環點時原始差值會接近整支長度,換算成較短的那一側

沒有時間來源時 `playbackRate` 主動歸 1,否則會停在上次的校正值。發布端只在 `!paused` 時送出,不發布停住的時間。

實測(以外部 WS client 假扮左螢幕發送已知時間):

| 送出 | 結果 |
|---|---|
| 大偏差 `time=20.0` | `seeking → seeked` 到 20.01 ✓ |
| 落後 0.2s | `ratechange → 1.03` ✓ |
| 超前 0.2s | `ratechange → 0.97` ✓ |
| 同步 | `ratechange → 1` ✓ |

左半那台發布間隔實測平均 **400ms**,與設定值一致。

## 11. 自訂推導的指標

以下三項 API 沒有,是自訂邏輯。

### 舒適度(`comfortLabel`)

以體感溫度為主,濕度高時往「悶」修正。

| 條件 | 結果 |
|---|---|
| 體感 ≥ 35 | 悶熱 |
| ≥ 30 | 濕度 ≥ 70 → 偏悶熱,否則偏熱 |
| ≥ 26 | 濕度 ≥ 80 → 微悶,否則溫暖 |
| ≥ 20 | 舒適 |
| ≥ 15 | 微涼 |
| ≥ 10 | 偏涼 |
| < 10 | 寒冷 |

### 體感趨勢(`feelsTrendLabel`)

比較現在與 3 小時後的體感溫度:差 ≥ +1.5 → 上升、≤ −1.5 → 下降、其餘 → 穩定。

### 蒸發感(`evaporationLabel`)

`index = ((100 − 濕度) / 100) × (1 + 風速 / 25) × (溫度 / 28)`

≥ 0.75 → 強、≥ 0.35 → 中等、< 0.35 → 弱。**無官方定義**,純自訂指標。

### 空氣狀態(`airStateLabel`)

比 AQI 分級再粗一階:≤ 50 清新、≤ 100 普通、≤ 150 稍差、> 150 混濁。

### 月相(`moon.ts`)

API 沒有月相,以 **2000-01-06 18:14 UTC 新月**為基準,除以朔望月 **29.530588853** 天取餘數。

```
illumination = (1 − cos(2π × 月齡 / 29.530588853)) / 2
waxing = 月齡 < 朔望月 / 2
```

已對照已知日期驗證:新月 0.1%、滿月 99.8%、上下弦約 45% 且盈虧方向正確。

**限制**:平均朔望月模型,未計入月球軌道離心率,上下弦會算出約 45% 而非精確 50%,誤差約半天。展示用足夠,非天文級精度。
